# Windows parity with async-profiler v4.6

The reference is upstream tag `v4.6`, commit `557276c2950c14a5ad7073e2bef5a16616309247`; the port version is `4.6-windows.1`. The Windows build reuses the common profiler, JVMTI instrumentation, recorders and converters. Native Windows backends replace the operating-system portions.

This is an implementation and verification inventory. [Not applicable on Windows](#not-applicable-on-windows) records platform exclusions and their reasons; [Environment-limited](#environment-limited) lists implemented paths that the test machine cannot exercise. Unless explicitly identified as v4.6 evidence, the runtime results below describe the v4.5 port. Its upstream suite gate covered 15 HotSpot JVMs, Temurin 8 to 27, Azul 11/17, GraalVM 17 to 25 and GraalVM EE 8/11, apart from the listed known failures: `RecoveryTests.numbers` on GraalVM (Graal's cost attribution) and one metadata-placement failure on GraalVM 17. The updated v4.6 suite has 172 active upstream test declarations (33 Linux-gated), plus Windows adaptations and variants; eleven commented-out process tests are excluded from these counts. Targeted JDK 27 runs pass 58 unique Java cases and all 80 native unit cases, covering the new features and symbol-dependent allocation and stack-walker paths. The legacy feature selection passes 17/17 on each of JDK 8, 11 and 21. The rate-limit fixture with harness-owned lifetime also passes on JDK 8/11/21/27, each 1/1 without skips. The elevated 15-JVM v4.6 gate has completed. Kernel and broker captures pass with PDBs matched to the running kernel. Wall-clock batch attribution and startup readiness pass the post-fix matrix; all seven Temurin versions complete without failures. Three JIT cost-attribution assertions (including Azul 11 C2) remain below their numerical threshold. The native-application initialization failure was subsequently fixed and validated by 75 initialization-order/agent-startup checks across all 15 runtimes. Unresolved intermittents from earlier runs are retained; the current results and TODOs are in [the upstream test inventory](tests/upstream/README.md#v46-full-gate).

## JVMs

HotSpot-family JDK 8, 11, 17, 21, 25, 26 and 27 are in scope, including GraalVM and Azul. The tables name the runtimes each path was checked on.

OpenJ9 is not supported. Upstream's J9 paths (JVMTI extension stack traces, J9 allocation sampling and wall clock) are not ported, and the Windows Java metadata and unwind layer reads HotSpot structures. A VM whose `java.vm.name` contains `J9` fails `-agentpath`, dynamic attach and `System.load` of the DLL with `OpenJ9 is not supported on Windows` before any hook is installed.

JDK 26 and 27 changes that reach Windows-specific code:

- JDK 26 removed `is_method_handle_invoke` from `PcDesc` and renumbered the remaining flags; handler proofs use each version's flag set. Method-handle call sites no longer restore SP from RBP.
- The method entry barrier stub is named `method_entry_barrier` on 25, `Stub Generator method_entry_barrier_stub` on 26 and `method_entry_barrier_stub (stub gen)` on 27; recognition binds the exact name per version. The generated barrier code is unchanged.
- JDK 26 appends a reference count to nmethod immutable data so relocated copies can share it. Handler, implicit-exception and PcDesc offsets keep the JDK 25 typed layout, and typed JavaThread exception fields are exported unchanged.
- JDK 27 inserted `CodeBlobType::MethodHot` before `NonNMethod` and `All`. WhiteBox code storage selects its heap type by the presence of `HotCodeHeapSize`, added in the same change.
- JDK 27's experimental hot code heap (`-XX:+HotCodeHeap`, JDK-8326205) is a fourth code heap inside the single reserved code cache. Upstream's four-heap lookup covers software stacks. HotSpot's single code-area exception registration also covers it, so compiled unwind records for relocated nmethods use the same RVA window and storage. Relocation posts `CompiledMethodLoad` for the copy; the original retires through the normal unload path. ETW captures on Temurin 27 with nmethods relocated into the hot heap before and during capture pass the plain, Java-only/CPU-ID and exception cases.
- JDK 26 `jmethodID`s are opaque and JDK 27 always compresses class pointers; the shared upstream code handles both. The Temurin 27 build has no JVMCI.

The saved-slot alias rule tracks frame-pointer provenance per GPR: no frame pointer; exactly entry-SP plus an offset, derived from RSP through MOV, LEA and ADD/SUB of an immediate; an unknown frame pointer from any other combination or a conflicting join; a pointer into an escaped frame object; or an exact address that may instead be such a pointer. RSP-based and exact stores are checked against the slot by byte range. Unknown frame pointers, indexed RSP stores and indexed stores from the slot upward invalidate it, as do stores through escaped pointers once the slot address itself escaped. A frame pointer escapes when it is stored or a call is made while a register holds it; afterwards loads and call results may hold escaped pointers. Two refinements keep legacy stack locking from widening provenance. A register-form SUB whose subtrahend is a frame pointer yields an offset, not a frame address: re-forming an address needs a frame operand again, which is tracked. This is the stack-lock recursion check `mark - rsp` of C2 `C2_MacroAssembler::fast_lock` (`MacroAssembler::fast_lock` before JDK 17), C1 `C1_MacroAssembler::lock_object` and Graal `MonitorSnippets.monitorenter` in their stack-locking paths. At a join, an exact address below the slot whose object escaped on every path into one side, meeting a non-frame or escaped-object value, stays an escaped-object pointer: it is one of the pointers premise (2) below already covers, like the lock-slot address that stack locking stores into the object header and a slow path's call result. An exact address that never escaped on its side, meeting such a value, keeps the exact address alongside the escaped objects: stores through it are checked against the slot by byte range for the exact address and invalidate it once the slot address escaped, and an escape records it like an exact address. This is an inflated-lock path where the lock slot is only written in place, meeting a slow path's call result; it relies on the same escaped-object premise. A call merges each register with a callee value exactly like a join, so these results do not depend on analysis order, and memory-form CMPXCHG leaves RAX unchanged or loaded from memory, never the stored register (Intel SDM). GraalVM 17/21 exception-stress captures then keep 0-2 stacks per run cut at unproven unwind data, against 241-281 before; their root counts are given above. Two premises come from the HotSpot and Graal sources rather than the code bytes. (1) Values entering a frame point into it only after one of its addresses escaped. Its incoming registers predate the frame; compiled code forms frame addresses only from RSP (C2 `BoxLockNode::emit`, C1 `LIR_Assembler::monitor_address`, Graal `StackLeaOp` through the `AMD64HotSpotRegisterConfig` RSP frame register); and the VM writes a live compiled frame only inside the lock record it was given (`BasicLock` through `ObjectSynchronizer`, `SharedRuntime::monitor_enter_helper`, `Runtime1::monitorenter`, `JVMCIRuntime::monitorenter`, biased-lock revocation and `Deoptimization::relock_objects`), in the orig-PC/deoptimization-rescue slot and the callee's return address (`frame::deoptimize`, `nmethod::set_original_pc`, `frame::patch_pc`), or with the value the frame restores into RBP (GC through `frame::update_map_with_saved_link`, continuation thaw through `patch_callee_link`). JVMTI local writes wait for deoptimization (`compiledVFrame::update_deferred_value`), and `BarrierSetNMethod::deoptimize` only reads the slot. (2) Every frame object whose address escapes lies below the saved slot and is accessed within its bounds. C2 keeps the slot in its in-preserve area above the lock and orig-PC slots and the allocator's spill region (`x86_64.ad` frame layout, `SharedRuntime::in_preserve_stack_slots`); C1 above spills, `BasicObjectLock`s and the orig-PC word (`frame_pad_in_bytes`, `FrameMap::finalize_frame`); Graal allocates `rbpSpillSlot` at entry-SP minus eight before any other slot and never reuses stack ranges (`AMD64HotSpotFrameMap`, `LSStackSlotAllocator`; 21.3 and 22.3 free the slot only in methods without debug information, which have no lock slots). These were checked in OpenJDK jdk8u, jdk-11/17/21-ga, jdk25u and mainline, JVMCI-8, and Graal `vm-21.3.12`, `vm-22.3.3`, `vm-23.0.6`, `vm-23.1.5` and `vm-25.2.4`. Only the last is the exact compiler of a tested build (GraalVM 25.2.4); the other Oracle GraalVM compiler commits are not public, and Enterprise-only compiler code is closed, so each store is decided by provenance in the code itself rather than by trusting the compiler. Programs that write the stack through `Unsafe` or JNI are outside this basis. An ordinary GraalVM 25 catch checkpoint passes the complete actual-context witness: one catch checkpoint, zero normal-path checkpoints, exact refreshed callback-certificate equality, exceptional-only call/return reachability, real handler-frame and two level-4 caller unwinds, and restoration through a certified JNI wrapper and call stub to an independently captured native parent PC/RSP/RBP. The witness checks five local Windows unwind operations and seven native PE frames; all 78 byte/metadata certificate regressions pass. The retained 186-byte call-stub prefix also passes 71 offline cases, with ten independently disassembled VEX XMM saves; no generated code executes in that replay. These establish actual HotSpot catch-path and local Windows-unwind evidence on a real stack; the asynchronously sampled ETW evidence is the exception-stress captures above.

A passive GraalVM 25 implicit-fault witness observes one real null-access fault and one catch checkpoint, with no observed normal-path faults or checkpoints. The Windows exception context remains byte-for-byte unchanged while HotSpot performs its own dispatch. Two precomputed local Windows unwind steps recover the same outer caller PC/RSP/RBP from the OS fault context as the independent catch walk; the latter also recovers the exact native parent baseline through two level-4 callers, the JNI wrapper and call stub. The faulting accessor is conventional C1, while the catch carrier is nonconventional level 4. Typed snapshot stamps own the exact parser inputs and compare current Method roots, metadata cells and bytes; raw carrier comparisons begin only after the source unwind proves its exact active return PC. The expanded typed-layout and snapshot units pass 309 and 521 checks across the 8/11/17/21/25/26/27 schemas. All 78 existing certificate regressions also pass. The implicit continuation PC is certified metadata and was not observed in this witness. Optimized faulting sources are not covered, and asynchronous ETW coverage of faults and handlers is the exception-stress captures above, which do not single out samples at those PCs.

The handler-eligibility reader also recognizes the JDK 25–27 immutable layout: unsigned two-byte handler offsets and an integer scopes-PC endpoint, all expressed in bytes relative to immutable data. Exported field types, object bounds, immutable size and pointer arithmetic are validated; malformed or unknown layouts decline proof. Typed negative tests and the unchanged-default GraalVM 25 capture below pass.

Unchanged-default GraalVM 25 code reports `method_entry_barrier`, and its compiled integer loop uses CMOVcc and VEX RORX. The port binds that exact stub and models those integer effects with conservative RBP/SP handling and strict RORX encoding checks. A further bounded extension recognizes scalar VEX arithmetic and moves, keeping XMM destinations separate from GPRs. Scalar stores invalidate saved-RBP proof under the same provenance rule; malformed and unsupported encodings retain the cutoff. Its 71 encoding/effect cases pass 1,526 Windows unwind contexts alongside the existing 1,130-context suite. A real GraalVM 25 level-4 scalar method, captured with explicit `-XX:UseAVX=2`, also passes 266 Windows unwind contexts over its owned code snapshot. The pinned decoder has a narrow native EVEX extension for unmasked scalar-double memory MOV, ADD and MUL; its boundary/relocation suite passes 25,467 boundary checks, 12,075 EVEX checks and 32 signed-rel32 range cases. The combined scalar effect suite passes 104 cases and 1,989 Windows unwind contexts. Fresh default GraalVM 25 and 21 level-4 scalar snapshots pass 288 and 199 contexts respectively without VM instruction-set overrides. Pre-25 layouts export `_nul_chk_table_offset` and `_nmethod_end_offset`, but not JVMCI's `_speculations_offset`, where an INCLUDE_JVMCI build ends the implicit-exception table. Adjacent exported fields end the table at `nmethod_end`. When exactly two ints separate them, they are `_speculations_offset` and `_jvmci_data_offset`, as declared between them by graal-jvmci-8, labsjdk 11 (jvmci-22.3) and JDK 17/21 `nmethod.hpp`; the table ends at the first, which must lie between the table start, the second and `nmethod_end`, and a nonempty table must then fill that extent exactly. Other layouts keep the absence proof: a zero first word at the validated typed begin proves only absence of entries, and the snapshot retains an explicit absence certificate without inventing an endpoint. GraalVM EE 8/11 legacy ETW captures, whose hot Graal methods carry implicit-exception tables, keep 1,986-1,999 of about 2,000 Java chains. OpenJDK 8/11 JVMTI `CompiledMethodLoad` reports code only up to the stub section (`insts_size`), while JVMCI 8, labsjdk 11 and JDK 17+ report the whole code range; the snapshot accepts either extent, the first bounded by the exported `_stub_offset`. Positive tables require an exact typed extent, valid unique source/continuation offsets and their own instruction-effect proof. Short or nonzero unknown probes, unsupported layouts and other SIMD/EVEX profiles remain unproven. Actual GraalVM 21/25 machine-code fixtures pass 1,130 native unwind contexts plus bad-encoding and register-clobber cases. The original strict CPU-alias broker case with the same compiler defaults passes: 2,466 complete physical Java chains from 2,468 samples, CPU IDs on every sample, zero CFI cuts/partials, and matching native/JFR/OTLP weights of 2,468,000,000 ns. The barrier is recognized and transport, unwind and metadata failure counters are zero. This establishes recovery for the measured default workload, while unsupported encodings and layouts retain the cutoff.

`-XX:+PreserveFramePointer` makes GraalVM 21's normal compiled-frame body use a conventional saved-RBP slot: its backend pushes RBP and establishes the frame pointer before allocating the rest of the frame, then restores it during frame removal. This supports the normal-body rule, but does not establish complete prologue, epilogue, runtime-stub or adapter coverage. It also does not add missing Windows unwind metadata to the separately built native-image compiler library.

Code-cache records can use HotSpot's diagnostic allocator when the JVM owner enabled `WhiteBoxAPI` at startup. ABI/range/layout checks validate the binding, and the profiler never changes the flag on attach. Its approximately 64 KiB buffer has VM lifetime and is reused across captures. This pool serves code-cache records; it is not a general solution for metadata placement.

Metadata registration groups adjacent owned allocations within the positive RVA bound while preserving independent allocation lifetimes and committed-coverage histories. Production-code tests verify rollback after a failed publication or release, decommit/recommit, historical proof before release, and foreign JIT reuse afterward without stale proof or a spanning range claim. Freed holes split clusters. A fragment that cannot obtain a reachable unwind record is withdrawn and reported, while representable survivors remain available. Code-cache exception registrations keep their original origins and handlers. The allocator also includes the final valid page of the 32-bit offset window. A cluster's record is the carrier (a hidden class on JDK 15+, a VM-anonymous class on JDK 11, whose JVMTI refuses to redefine it; none on JDK 8, whose JVMTI may), a shared native copy inside that window, or a native copy in a free granule directly below the cluster, which then becomes the table's range base. Measured ETW stack walks consult only growable tables and images, never HotSpot's `RtlAddFunctionTable` registration, and unwind through data PCs whose range base lies in a separate allocation below them; `RtlLookupFunctionEntry` agrees. A user-mode lookup does not fall through from a containing growable range to another table, so a range never extends over memory the profiler does not own. Default-launch layout probes needed the lower base for 12/70 GraalVM 21 and 1/70 GraalVM 17 launches, whose CDS archive and class space had no free granule inside the window. Nonadjacent allocations, excessive spans and storage occupied on both sides remain placement limits, with diagnostics specific to the failed area. Code-cache records keep the explicit WhiteBox requirement when the 4 GiB above the code cache is full. On GraalVM the blocker is libgraal: each compiler isolate reserves 32 GiB of address space, placed directly above the code cache. Default launches found no free granule in 94/140 GraalVM EE 8, 5/140 EE 11, 4/140 GraalVM 17, 3/138 GraalVM 21 and 2/60 GraalVM 25 launches, and in none of 40 launches each of Temurin 8/11/17/21/26/27 or 70 of Temurin 25. `-XX:-UseJVMCINativeLibrary` runs the same Graal compiler as Java code (jargraal), without isolates; compiler threads then show Graal's Java frames and warm up more slowly. With it, code and metadata records found storage in 95/95 EE 8 launches and code records in 40/40 launches each of EE 11 and GraalVM 17/21/25. It is the workaround for JVMs without VM code storage: GraalVM EE 8's WhiteBox has no code-blob allocator, so WhiteBoxAPI there leaves ordinary placement in effect. The storage error names the remedy that applies. JDK 8 metadata found no storage in 52/70 default EE 8 launches and 0/40 Temurin 8 launches; the JDK 11 carrier reached every EE 11 metadata allocation in 70 launches.

## Not applicable on Windows

- `kprobe`, `kretprobe`: kernel function probes need a kernel-mode driver, which the port does not ship.
- `bus-cycles`, `L1-dcache-load-misses`, `LLC-load-misses`, `dTLB-load-misses`: the Windows HAL enumerates no exact equivalent source, and broader counters are not substituted; requests fail explicitly.
- OpenJ9: the Windows Java metadata and unwind layer reads HotSpot structures; a J9 VM is rejected at load before any hook is installed.
- `perf_event_open` specifics (kernel call chains, programmable event attributes): Windows has no perf_events; ETW and the polling engines take their place.
- `.debug_frame` DWARF unwinding: PE images carry Windows unwind metadata, which `cstack=dwarf` uses.
- POSIX signals: `signal=` selects logical callback IDs 1–255.
- Linux tracepoint names: Windows provider tracepoints are named by GUID and event ID or name.
- Linux `/proc` fields: Linux-specific process breakdowns are labeled unavailable.
- `features=vtable,comptask` with ETW: ETW stack events carry no sampled registers or compiler-task state; requests fail explicitly.
- `uprobe` at call sites: a displaced CALL pushes an out-of-module return address that user mode cannot replace on the CET shadow stack.
- `uprobe` in epilogue interiors: an INT3 inside an epilogue changes how Windows unwinds the epilogue positions before it.
- `uprobe` behind unresolved jump tables: control-flow proof cannot reach code entered only through an unresolved indirect jump.
- `uretprobe` without unwind data: without an exception-directory row the function's extent is unknown, so code shared with another such function cannot be excluded.
- `uretprobe` where a language handler's call returns to an epilogue start: Windows skips the frame's handler for that return address, while an INT3 there would let it run with data never meant for it.
- Read-only `mem:` watchpoints: x86 debug registers have no read-only mode, as on upstream Linux x86.
- `alluser` with provider tracepoints: provider event headers do not record the privilege mode that emitted an event.

## Environment-limited

Implemented, but not exercisable on the test machine (AMD Family 26, Windows 11 as a Hyper-V root partition):

- CPUID leaf 0x15 TSC rate and Intel PMU and raw-event programming: the processor is AMD; CPUID leaf 0x15 exists only on Intel.
- AMD host/guest filtering: in a Hyper-V root partition both modes count everything.
- `cache-references`, `ref-cycles`: this AMD HAL enumerates no matching source.
- RTM: XBEGIN's abort path from a relocated probe needs RTM hardware, which Zen 5 lacks.
- JVM hardware TSC: HotSpot takes the TSC rate from the CPU brand string, which AMD processors lack, so the JVM uses QPC.
- Broker launcher/ACL layouts other than the same-user default, and broker PMU models other than this AMD one; low-integrity targets are checked.
- Sharing the ETW profile configuration between logon sessions: it needs a session-0 SYSTEM capture, which the test setup does not create.
- Live tracepoint split stacks: they need a provider that splits a stack across records.
- JVMs without PDBs: JDK 8 allocation profiling, TLAB and TTSP need the exact `jvm.dll` PDB; GraalVM and Azul publish none, so those tests skip there.
- GraalVM EE 8 has only Oracle's commercial Flight Recorder: `jfrsync` fails explicitly and `jdk.jfr` readers are absent.
- libgraal: the GraalVM 17/21 compiler library's PE unwind table covers only its C runtime, so compiler-thread stacks end in its native-image code; GraalVM 24 and later emit the table.
- JDK 8/11 builds without the JDK-8308341 fix (before 8u391 and 11.0.21) give JVM threads no Windows names; a JVM such a build creates through the C API is rejected with a warning, and no such build is installed.
- Other Windows versions: only Windows 11 is available; the high-resolution timer needs Windows 10 version 1803 or later.
