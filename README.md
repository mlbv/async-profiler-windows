# async-profiler for Windows x86-64

A standalone source port of async-profiler v4.6, version `4.6-windows.1`. The build produces `asyncProfiler.dll`, `asprof-helper.exe` for ETW control, cleanup and preloaded native launches, the `asprof.exe` CLI, the `jfrconv.cmd` converter launcher, and a JAR with the Java API, agent entry points and converters. IntelliJ IDEA and JetBrains' profiler DLL are not required. As upstream, it is licensed under the Apache License 2.0 ([LICENSE](LICENSE)); the upstream source revision is in `core/UPSTREAM`.

The [compatibility inventory](COMPATIBILITY.md) maps upstream v4.6 features to their Windows implementations, verification evidence and platform limits. The Windows copy of upstream's test suite is in `tests/upstream`. The previous v4.5 suite passed on the target JVMs apart from the listed known failures. Targeted v4.6 verification on JDK 27 passes 58 unique Java cases and all 80 native unit cases, and the legacy feature selection passes 17/17 on each of JDK 8, 11 and 21. The post-fix elevated v4.6 gate has completed on all 15 JVMs, with no failures on Temurin 8/11/17/21/25/26/27. Three JIT cost-attribution assertions fall below their numerical threshold. A GraalVM 17 native-application initialization failure was then fixed and validated by all 75 initialization-order and agent-startup checks across the same 15 runtimes. The test inventory records the complete matrix, follow-up evidence and unresolved intermittents from earlier runs.

This is a preview release, tested on one machine: an AMD Family 26 (Zen 5) processor running Windows 11 Insider build 26340 as a Hyper-V root partition. Intel processors and generally available Windows releases are untested; the inventory's [environment-limited](COMPATIBILITY.md#environment-limited) list names what this machine cannot exercise. Versions are named `<upstream version>-windows.<n>`, where `n` counts the port's releases on that upstream version.

Target JVMs are HotSpot-family JDK 8, 11, 17, 21, 25, 26 and 27, including GraalVM; per-version evidence is in the compatibility inventory. OpenJ9 is not supported: loading the DLL into it fails with `OpenJ9 is not supported on Windows`.

[Compatibility inventory](COMPATIBILITY.md) covers native parser options, event families, checked paths and remaining gaps.

## Build

Requires Windows x86-64, JDK 17+, CMake, Ninja, Clang with the Windows GNU target, and a MinGW-w64 sysroot with static C++ and pthread libraries. The profiler uses Windows SEH, so Clang is required for the native build.

```powershell
powershell -NoProfile -ExecutionPolicy Bypass -File .\build.ps1 `
  -JdkHome C:/jdk-25 `
  -ClangCxx C:/llvm/bin/clang++.exe `
  -MingwRoot C:/mingw64
```

The output is `build/asyncProfiler.dll`, `build/asprof-helper.exe`, `build/asprof.exe` and `build/asprof-windows.jar`. The native binaries carry no debug information; debuggers, and the profiler for its own frames, find their PDBs beside them. Add `-Package` to create `build/asprof-windows.zip` and, as upstream's debug package, `build/asprof-windows-debug.zip` with the PDBs. The ZIP contains our compiled DLL, ETW helper, `asprof.exe`, JAR and `jfrconv.cmd`, the public C API header, and the license. It contains no JetBrains binary. `-JavaOnly` rebuilds the JAR without rebuilding the native binaries.

As upstream's `make ni`, `-NativeImage` also builds `build/jfr-converter.exe`, a GraalVM native image of the converter that the ZIP does not include. It needs `native-image` in `-JdkHome` (a GraalVM, which uses the MSVC x64 build tools). The image uses Native Image's default x86-64-v3 CPU baseline and needs the Visual C++ runtime (`VCRUNTIME140.dll`; Microsoft's Visual C++ Redistributable for x64). It parses its command line as the `java` launcher does, including unquoted wildcard expansion; leading `-D`, `-X` and `-J` options set Native Image runtime options, `-Xss` sizes the converter thread (default 2 MiB), and `-agent` options are rejected.

The native build statically links its C++ and pthread runtime. System Windows DLLs supply operating-system services and DbgHelp symbol handling.

`asprof.exe` needs no Java runtime; as upstream's package, this one needs Java only for `jfrconv`. The JAR's `one.profiler` API/SDK classes and upstream converters target Java 8: older applications can use the API from the same JAR, and `jfrconv.cmd` runs the converters on Java 8+. The JAR includes the HTML templates needed for standalone conversion.

The same JAR exposes upstream's Java agent entry points. For Java-agent startup, pass the separate native library explicitly, for example `java -Done.profiler.libraryPath=C:/profiler/asyncProfiler.dll -javaagent:C:/profiler/asprof-windows.jar=start,event=cpu,jfr,file=cpu.jfr -cp application.jar com.example.Main`. This path has been checked on Java 8.

## Use

`asprof.exe` takes upstream v4.6's command line, `asprof [action] [options] <pid>`; `asprof -h` lists its actions and options, and upstream's [ProfilerOptions.md](https://github.com/async-profiler/async-profiler/blob/v4.6/docs/ProfilerOptions.md) describes them. Version 4.6 removes the embedded HTTP server and replaces thread-ID filters with thread-name patterns and the Java thread-filter API.

```powershell
.\asprof -d 30 -f cpu.html 12345
.\asprof -e wall -d 30 -f wall.jfr 12345
.\asprof -e alloc --alloc 64k -d 30 -f alloc.jfr MyApplication
.\asprof start -e lock --lock 1ms -f locks.jfr jps
.\asprof stop jps
.\asprof jcmd 12345 VM.flags
```

`<pid>` is a process ID, `jps` for the most recently started attachable JVM, or an application name as `jps` shows it. As upstream, `collect` is the default action and profiles for `-d` seconds (default 60); Ctrl+C stops it early. Without `-f`, the profile is printed to stdout. The agent's log goes to stderr. Existing output files are overwritten. The exit code is 1 for CLI and attach errors, 255 when the JVM cannot load the DLL, and otherwise the agent's status (100 for rejected arguments, 200 for failed commands). As jattach, the actions `load`, `jcmd`, `threaddump`, `dumpheap` and `inspectheap` print HotSpot's reply after `JVM response code = STATUS` and exit with its status (for `load`, the agent's return code) modulo 256.

`asprof.exe` attaches as jattach does: a thread it creates in the target calls jvm.dll's attach entry point, and the reply returns through a pipe that only the target process may connect to, using HotSpot's version 2 protocol where the JVM advertises it. As jattach allows the attach listener 6 seconds to start, the attach fails if the target does not run that thread within 6 seconds, for example while it is suspended. The thread's code and data then stay allocated in the target so that a late run cannot crash it, and the request is disarmed so that a late run does not execute it. The operation itself is unbounded, as upstream and the JDK's client, and the wait ends when the target exits or on Ctrl+C. `ps`, `jps` and application names find only the current account's JVMs. The DLL path and jattach arguments reach HotSpot in the system ANSI code page and must be representable in it; profiler options are UTF-8.

As upstream, attaching to JDK 21 or later prints no dynamic-agent warning. A running JVM checks `EnableDynamicAgentLoading` after loading the DLL and before calling `Agent_OnAttach`; while the DLL loads, its `DllMain` marks a default flag as set on the command line by writing the flag through jvm.dll's exported VMStructs tables, the only work it does under the loader lock. A startup `-agentpath` loads the DLL before the VM exists and leaves the flag unchanged.

Option values other than `-o` and `--ratelimit` cannot contain commas or control characters, which would split the agent's argument list; upstream passes them through. The CLI translates the comma-separated `--ratelimit` list to the agent's semicolon-separated form. Relative `-f` paths resolve against the calling directory after target-side `%` expansion, and missing parent directories are created. A relative `--libpath` is a path, not a library name. Linux tracepoint names are not resolved. `--dot` is accepted as documented upstream.

`--jfrsync profile` combines native profiler samples with regular JVM JFR events, including GC and application-defined events. Individual event settings use `+event#setting=value`, for example `--jfrsync '+jdk.JavaExceptionThrow#stackTrace=true'`. The JVM recorder remains necessary for JVM-specific events that the profiler itself does not generate.

`--ratelimit cpu:1000,alloc:200,span:100` caps JFR events per second for each selected category. The categories are `cpu`, `alloc`, `lock`, `wall`, `nativemem`, `nativelock`, `trace` and `span`; event types in one category share its budget. Unused budget permits a burst up to twice the limit, `0` suppresses that category, and omitted categories are unlimited. For `-agentpath`, write `ratelimit=cpu:1000;alloc:200;span:100`. These limits govern JFR event emission.

`--ithread '*worker*'` includes threads by name and `--xthread '*idle*'` excludes them. Repeat either option for multiple patterns; exclusions win when both match. Patterns are checked when profiling starts, when Java threads start and on each dump. The agent option `filter` enables an initially empty selection controlled by `AsyncProfiler.addThread()` and `removeThread()`; it takes no value. Windows applies this selection to CPU, ETW, wall, probe and provider-tracepoint sampling, extending upstream's wall-only contract. Wall-clock idle detection uses high-resolution per-thread cycle time converted at the invariant-TSC rate. The baseline is captured while the target is suspended; short wakeups invalidate cached stacks. Windows omits upstream's Linux EINTR shortcut because its syscall number and first argument do not identify a particular blocked call.

An `http://` or `https://` destination in `-f` sends OTLP profiles directly to an OpenTelemetry endpoint using Windows' WinHTTP client. If no path is given, the path is `/v1development/profiles`; for example `asprof --loop 60s -f http://localhost:4318 12345`. Uploads run in the target process, so the endpoint must be reachable from that process. HTTP transport and CLI uploads pass integration checks, including origin and proxy authentication with percent-encoded passwords containing `@`, `:`, `%`, `/` and `+`. HTTPS transport and certificate validation remain untested. Uploads have a ten-second operation deadline. On cancellation, the call drains outstanding WinHTTP callbacks before returning, so return time can exceed that deadline; cancellation has no strict absolute completion bound. Proxy selection reads `http_proxy`, `https_proxy` and `all_proxy`; proxy URLs must use `http://`, because WinHTTP does not support HTTPS proxies. `no_proxy` accepts domain names, IP addresses, CIDR networks and `*`. OTLP `service.name` is taken from `otel.service.name` / `OTEL_SERVICE_NAME`, then `otel.resource.attributes` / `OTEL_RESOURCE_ATTRIBUTES`, with system properties taking precedence over their environment counterpart; if none is set, the attribute is omitted.

HTML profiles combine the flame graph and tree view in one page and display the recorded metric's units. The converter's `--tag` accepts a Java regular expression matching the entire span tag, for example `jfrconv --tag 'http\..*' profile.jfr http.html`. With `--latency`, the same span must satisfy both filters.

CPU sampling uses per-thread CPU-time deltas and suspended-thread context capture. CPU and cycle capture validates the measured thread's creation time against the opened local thread before sampling, so a reused thread ID cannot receive another lifetime's accumulated weight. Per-thread CPU time is `QueryThreadCycleTime` converted at the invariant-TSC rate. The rate is exact from the Hyper-V reference TSC page from which Windows derives QPC (verified at start) or from CPUID leaf 0x15; otherwise it is calibrated against QPC at start, which takes at least 20 ms and bounds the rate's error against QPC to 20 ppm. Without an invariant TSC, CPU sampling fails explicitly. `alluser` uses GetThreadTimes' user split, which advances in scheduler ticks (15.625 ms on the tested system). Any interval is accepted: a high-resolution timer polls this process's threads once per slot of half the interval, or of an even fraction of it no longer than 50 ms, but at least 1 ms, at a random point of each slot so that no periodic workload stays between polls. A thread is sampled at the poll nearest its interval boundary unless it is sleeping, and each sample's weight is the thread's exact CPU time accumulated since its previous sample. JFR and OTLP report the requested `cpu`, `itimer` or `ctimer` event. This backend does not implement Linux `perf_event_open`, kernel call chains, or programmable PMU events. Wall-clock sampling reuses the upstream scheduling and batching logic with Windows context capture. Its high-resolution timer and process-scoped thread inventory have been checked at 5 ms on Java 8/11/17/21, including sleeping batches and exact duration weights. A timer wait can end up to one system timer period late (about 0.5 ms here, measured at start), so each tick samples at least upstream's 8 threads and as many more as it takes to cover every thread once per interval in groups two periods apart. An unbatched capture costs about 20 µs here, so that cadence holds while threads × 20 µs fits in the interval less one timer period (about 25 threads at 1 ms, 225 at 5 ms); larger populations stretch the cycle, and each sample keeps the nominal interval weight.

`--event cycles` samples Windows' reported per-thread CPU cycle counts, including user and kernel work. Its interval is a count threshold (default 1,000,000), while the Windows polling cadence is separately fixed at 1 ms. It is a polling sampler, so the requested threshold is not a hardware interrupt period. Actual count deltas are retained as sample weights. Those counts are not converted to elapsed time or substituted for other PMU events. `itimer` and `ctimer` select the Windows CPU-time backend.

The experimental ETW backend provides interrupt-driven timer and PMU sampling. `list` prints this host's `etw:SOURCE` names and interval ranges. `etw:Timer` uses nanoseconds; other sources use event counts. `instructions`, `cache-misses`, and `branch-misses` alias matching Windows sources. Additional aliases resolve only when the host enumerates their exact counterparts: `branch-instructions` uses `BranchInstructionRetired` or `FRRetiredBranches`, `cache-references` uses `LLCReference`, and `ref-cycles` uses `UnhaltedReferenceCycles`. `list` shows each resolved source or its unavailability. Bus-cycle and load-only cache/TLB aliases fail explicitly where no equivalent source is implemented; broader counters are not substituted. `branch-instructions` counts the expected retired branches on the tested AMD host, which has no source for `cache-references` or `ref-cycles`. Without an explicit interval, the timer reuses an existing timer profiler's rate, or defaults to 1ms; PMU sources default to 1,000,000 events within their supported range. `etw:TotalCycles` is distinct from the polling `cycles` backend. Upstream's `cpu-clock` forces perf_events; on Windows it forces the ETW timer, locally or through the broker, and fails explicitly when neither is available. As upstream selects perf_events, `record-cpu` or `target-cpu` (and `fdtransfer`) select the ETW timer for `cpu`, and `etw:TotalCycles` for `cycles`; the polling `itimer`, `ctimer` and `wall` engines reject both options.

Local ETW capture requires the target to have `SeSystemProfilePrivilege`, normally through administrator elevation. The broker configuration keeps the JVM at ordinary medium privilege. As upstream's `--fdtransfer` starts its fdtransfer server, an elevated `asprof` under the same Windows account starts `asprof-helper.exe --etw-broker PID PIPE --once` beside the DLL. That broker serves one profiling session: it exits when the session stops, or after 30 seconds if none connects. A non-elevated `asprof` rejects `--fdtransfer` before attaching.

```powershell
# Elevated terminal; replace 12345 with the target JVM PID.
.\asprof -e etw:Timer -d 10 -f timer.jfr --fdtransfer 12345
```

Agent and C API users can run a persistent broker from an elevated terminal with `asprof-helper.exe --etw-broker PID [PIPE]` and pass `fdtransfer` or `fdtransfer=PIPE` to the agent; both default to `\\.\pipe\async-profiler-<PID>`. Remote pipe clients are rejected. The broker validates the actual client's PID, creation time and user SID; the target validates the actual elevated server and its user SID. Java metadata and stack decoding stay in the target, while the worker owns ETW control and streams bounded raw event records.

Profile/PMU records with an unknown process ID need an explicit target-PID StackWalk at the same original QPC timestamp and thread ID before they can cross the pipe; a remembered thread ID alone never establishes ownership. Broker `cstack=no` still collects these physical ownership stacks internally, including for native targets, but suppresses them in stackless output. This retains stack-collection overhead. `windows_etw_broker_foreign_profiles` counts proven foreign profiles, `windows_etw_broker_unattributed_profiles` counts unresolved global records, and `windows_etw_broker_potential_target_loss` counts unresolved candidates associated with target-thread hints. Unproven records are not charged as target samples; inspect these diagnostics when assessing completeness. Thread/kernel-image metadata excludes emitter details, payload tails and extended stacks. The private wire is versioned; use DLL and helper binaries from the same build.

The launcher stays query-denied and creates a separate worker with a private primary token and restrictive process, thread and default-object permissions established before the worker starts. Before enabling capture, the worker checks its own and its watchdog's permissions. The ordinary target receives only process/token identity-query access, with no memory access, token control, handle duplication or controller-thread access. A runtime test deliberately changes a watchdog thread's query permissions and verifies that activation fails before sampling.

Internal recording loops reuse the session's worker. A persistent broker also serves successive sessions: normal stop/start reuses the same target-bound worker, and after a client disconnects, which ends its current capture, the worker accepts another connection for the pinned target. Target or launcher loss stops the worker, and a detached watchdog restores the sampling interval after worker termination. Fatal transport failures make stop report the first recorded Windows error; successfully finalized partial recordings remain readable. Compiled Java callers, reconnect, internal loops, kernel identities, target/worker/launcher termination, restored intervals and matching JFR/collapsed/OTLP weights are checked with GraalVM 25. Raw `rC0` sampling through the broker is checked on AMD Family 26 at a 1,000,000-event period, including source removal and exact exported weights. Bare `fdtransfer` uses the default endpoint; explicit empty `fdtransfer=` rejects before capture. The helper does not elevate the JVM or request an elevation prompt. A low-integrity target captures through the broker; other launcher/ACL layouts and broker PMU models are environment-limited (see COMPATIBILITY.md), and different-user administrators and SYSTEM brokers are outside the supported same-user configuration.

ETW uses a private system logger and filters captured samples to the target process. Unlike upstream's per-process perf_events, each ETW source's sampling interval and the PMC overflow-source selection are machine-wide, so concurrent captures share them. Timer captures share the timer; PMC and raw captures share the selected source, independently of timer captures. Concurrent PMC captures must select the same source; otherwise the later one fails, naming the process whose capture holds it. A source runs at the finest interval its captures request, and an unspecified interval is the event's default. Each capture adds the shared interval of every sample it receives to a running total and records a sample, weighted by that total, once the total reaches its own interval. Weights therefore stay exact, apart from a final remainder below one interval at stop, and each capture's sample rate stays close to its request. When captures join or leave, each sample counts the interval in force at its timestamp, ordered against the QPC time read just before the change. A CPU's first sample after a change may still have been timed by the previous interval, so each change can misweight one sample per CPU by the difference between the two intervals. Local targets and broker workers record their shares in a machine-wide registry; the broker forwards interval changes to its target ahead of later samples. The first owner saves the previous interval and the last restores it, including through the watchdog of a terminated last owner. An owner whose watchdog also died is removed, and its session stopped, once its process ID and creation time prove it gone. Profilers outside async-profiler keep the previous rules: a capture can use an existing timer rate it did not set, but not change it; an active PMC profiler prevents selecting overflow sources; and the interval is not changed or restored while another profiler uses it. Stopping the private session releases its hardware counters; Windows exposes no documented getter/clear operation to restore a previous dormant overflow-source list.

The registry is a section and mutex in a private namespace whose boundary descriptor requires the Administrators SID and High integrity. An ordinary-privilege process, including a target in the same session, can neither create nor open that namespace, so it cannot pre-create or reach the registry. Windows deletes a private namespace with its last handle, so every owner and watchdog keeps one; when the last owners and their watchdogs all die, the original interval goes with it (see COMPATIBILITY.md). Sharing between logon sessions, such as with a service in session 0, is environment-limited (see COMPATIBILITY.md). A broker target can join or be refused through its validated request; it cannot write records, release another owner's share or choose the restored interval. Builds with another registry layout use another name and treat these sessions as external profilers.

The experimental `page-faults` event uses ETW fault categories 10–15 and excludes hard-fault completion records. Intervals are per-thread event counts, defaulting to one fault and supporting logical periods through 9,223,372,036,854,775,807 events. The target applies the logical period after every physical event is captured; a larger period does not reduce ETW collection overhead. Faults a thread takes after logging its end are not counted. As perf records a fault with its registers, a user-mode fault's stack starts at the faulting PC without kernel fault-handler frames; kernel-mode faults keep theirs. Fault `alluser` filtering requires a nonzero user-space fault PC.

`context-switches` samples a thread when it is switched out, with upstream's per-thread period (default 2) and the page-fault interval range. ETW logs a CSwitch stack for the thread being switched in, so each switch-out takes the stack logged at that thread's next switch-in: the thread cannot run in between, so that stack is its stack at the switch-out and names its process. The sample keeps the switch-out's timestamp and CPU. A switch-out is reported once its thread runs again, as upstream's signal is delivered on resume; threads still switched out when capture stops are not reported and are counted by `windows_etw_software_router_unresolved_switches`. Switch-outs after a thread's end event, including its terminated switch-out, are not counted. Context switches happen in kernel mode, so `alluser` excludes all of them, like upstream's `exclude_kernel`. A lost event breaks a thread's switch sequence; `windows_etw_software_router_sequence_breaks` counts the dropped switch-outs.

Both software events assemble ETW's separate kernel and user stack parts per thread, locally and through the broker. ETW defers a thread's user part until it returns to user mode and logs it once per kernel-mode interval, tagged with one of the interval's stack keys; later keys of the interval share it, as `windows_etw_software_shared_user_stacks` counts. Earlier keys without a user part, faults nested in another fault's handling (ETW logs no stack for them) and faults of threads that never return to user mode keep their weight with explicit incomplete-stack markers; nested faults still receive the interval's user part. Native recordings, local and brokered, recover complete workload chains for faults at periods 1 and 5 and switches at periods 1 and 3. Java recordings on Temurin and GraalVM 25, local and brokered, cover thread churn, twelve consecutive captures, `cstack=no`, `record-cpu`, `target-cpu` and `alluser` with matching JFR, collapsed and OTLP weights. Faults inside Graal-compiled methods mostly stop at the unproven-CFI boundary described below.

Raw PMU selectors accept `rHEX`, `cpu/rHEX/`, and `cpu/event=...:umask=.../` descriptors. The CLI also accepts commas inside the descriptor and normalizes them to colons. Event codes are processor-specific. Registration is transient and scoped to this processor model; it does not change persistent registry settings. Omitted periods use the supported default; explicitly out-of-range periods fail. Concurrent captures of the same descriptor share one registered source, which the last owner removes. Raw and descriptor captures, exact weights, rollback and source removal have been checked on AMD Family 26; Intel and extended AMD programming remain unverified.

Windows provider events use `--event 'trace:{PROVIDER-GUID}/ID[/VERSION]'` or `--event 'trace:{PROVIDER-GUID}/@EventName'`. Replace the GUID and event identifiers with the application's published values. Name selectors use Windows TDH metadata and support TraceLogging names containing supplementary Unicode. Event periods are counts: `-i 10` records every tenth matching event independently for each thread, with weight ten. Period filtering happens after ETW delivery, so ETW continues capturing matching event stacks. The exact selector is retained in JFR and converted profile metadata.

```powershell
# Replace the provider GUID, event ID and optional version with real values.
.\asprof -e 'trace:{e50fb813-9e08-40dc-a8af-3390db1dbbf4}/1/7' -i 1 -d 10 -f events.jfr 12345
.\asprof -e 'trace:{2a94e71b-655a-4f69-8c64-302d17032ae9}/@燃烧𠮷' -i 10 -d 10 -f named-events.jfr 12345
```

Provider collection uses an ordinary ETW session with a cleanup watcher. It supports an elevated target or an ordinary target connected to its same-user elevated broker. Broker tests verify Unicode TraceLogging names with primary payloads stripped, per-thread periods including short-lived threads, and foreign-PID exclusion. Kernel-Process ImageLoad ID 5/version 0 recovers its Java/native caller, including repeated broker capture with two simultaneously resident fixtures at distinct preferred bases. A colliding-preferred-base fixture produced an additional genuine ImageLoad event; collection retains every matching event rather than equating event counts with LoadLibrary calls. `cstack=no` retains Java callers; `record-cpu` and `target-cpu` use the captured processor index. `alluser` fails explicitly because provider headers do not establish the privilege mode that emitted an event. Attribution uses the event header's PID; providers describing a target through a payload PID require a separate attribution contract. Cross-record kernel/user split stacks use a bounded joiner after primary selection. Delayed continuations retain the primary timestamp, CPU and weight; unresolved selected pairs fail stop, and ambiguous or repeated correlation keys fail explicitly. Live split-stack capture is environment-limited (see COMPATIBILITY.md). Thread lifetime tracking recognizes Kernel-Process manifest versions 0/1 and rejects unknown or ambiguous lifetimes. The tested GraalVM 25 runs used explicit `-XX:+UnlockDiagnosticVMOptions -XX:+WhiteBoxAPI` at JVM launch for Java unwind storage.

ETW correlates sample and stack events by original QPC timestamp and thread ID, including separate user/kernel stacks. Compiled Java PCs expand into method names, inline scopes, bytecode positions, line numbers, and C1/compiled frame types. Interpreter bodies transport saved bytecode addresses through Windows unwind records; entry code transports a method address after its slot becomes valid. The decoder replaces those addresses with interpreted Java methods, bytecode positions, and line numbers. Compilation, unload, class preparation, and successful class changes copy metadata while it is valid; timestamped versions and memory-allocation lifetimes prevent address reuse from renaming old samples. Application classes and class loaders are not retained. Snapshots are released when recording data resets. `windows_java_metadata_failed` reports failed snapshots; `windows_java_unmapped_vm_pcs` counts generated PCs without method metadata.

Compiled physical callers use a Windows growable function table built from HotSpot frame sizes and upstream's prologue/epilogue handling. Ordinary `RtlAddFunctionTable` registration was insufficient for ETW in the native generated-code fixture; growable registration recovered its complete caller chain. The added entries use HotSpot's existing exception handler, and the JVM retains ownership of its original registration. C1 and optimized Java caller chains, JVM exceptions during table updates, class unloading, reset, and VM exit have been exercised. `windows_java_unwind_publications`, `windows_java_unwind_failures`, `windows_java_unwind_unsupported`, and `windows_java_unwind_first_error` describe this bridge. Active registrations return to zero after stop.

Mixed compiled/interpreted stacks and framed runtime stubs now recover native thread roots on the tested HotSpot 17, 21, 25, 26 and 27 runtimes, including loops running in OSR-compiled code. Interpreter-only method and bytecode-position decoding has also been exercised on 21, 25, 26 and 27. Interpreter transport preserves the independent sender stack pointer used by compiled-to-interpreter adapters. A single unmodifiable hidden bootstrap class holds fixed unwind records within the JVM metadata address range; it has bootstrap lifetime and retains no application loader. JVM memory-release imports retire metadata registrations before their allocations are released.

Interpreter codelets supply entry boundaries and kinds. Frame setup has separate rules before the frame anchor, after sender-SP initialization, after saving the method, and after saving the bytecode pointer. This avoids reading an uninitialized bytecode slot during method entry. Ordinary bodies need two unwind steps and each metadata allocation uses one generic record, reducing the interpreter-only fixture from roughly 22,000 entries to 1,000–1,100. Unknown or ambiguous setup sequences reject capture instead of guessing. `windows_java_unwind_codelets` reports discovered codelets.

Code-cache unwind records require positive 32-bit RVAs from the original code-cache base. Other reservations, on GraalVM libgraal's 32 GiB compiler isolates, can leave no free allocation within that window; COMPATIBILITY.md lists the measured frequency per JVM. For those layouts, start the JVM with `-XX:+UnlockDiagnosticVMOptions -XX:+WhiteBoxAPI` to permit a small VM-owned code-cache buffer, or on GraalVM with `-XX:-UseJVMCINativeLibrary`, which avoids the isolates and also serves GraalVM EE 8, whose WhiteBox has no code-blob allocator. The storage error names the applicable flags. The profiler validates HotSpot's diagnostic allocator bindings and never changes the flag on attach. This optional path is tested on HotSpot 17, 21 and 25; on 26 and 27 its allocation and table publication are checked without ETW capture, including JDK 27's hot code heap. Its approximately 64 KiB buffer has VM lifetime and is reused across recordings; `windows_java_unwind_code_cache_pages` and `windows_java_unwind_code_cache_bytes` report its use. Code-cache registration origins and the JVM's original exception tables remain unchanged.

Metadata unwind records use an immutable class-backed carrier (a hidden class on JDK 15+, a VM-anonymous class on JDK 11), a shared native copy within the RVA window, or a native copy in the free granule directly below the allocation, which then becomes the registration base. JDK 8 has no carrier because its JVMTI may redefine VM-anonymous classes. Adjacent metadata allocations can share one bounded registration, allowing a carrier below a higher allocation to remain reachable. Each allocation retains its own lifetime and proof history, and tables cover committed portions only. Production allocation probes verify failed-publication rollback, decommit/recommit, release and reuse by a foreign JIT without retaining a stale range claim. `--probe TARGET` is a Windows shorthand for `-e TARGET` with a native symbol.

Native memory profiling intercepts named dynamic CRT imports, supported aligned/recalloc functions, intercepted dynamic lookups, and imports in DLLs loaded after profiling starts. It records requested malloc sizes and corresponding frees. Private or statically linked allocators and previously cached function pointers remain outside that coverage. Windows heap-block tracing is a different measurement and is not substituted for malloc request sizes.

Native lock tracing covers critical sections and exclusive/shared SRW locks. Bare-symbol native probes use per-thread hardware execution breakpoints, preserve the original instructions, and intercept thread creation to cover new native threads. A debugger using all hardware breakpoint slots causes probe startup to fail.

Software probes use `--event 'uprobe:C:/path/loaded.dll+FILE_OFFSET'` or the Windows symbol form `uprobe:module.dll!symbol[+OFFSET]`; return probes take the same forms with `uretprobe:`. The file offset is mapped through PE sections, and the target DLL must already be loaded. Both use an owned INT3 and displaced execution without consuming a hardware breakpoint slot, and work in compatible and strict CET processes. Recording periods are per thread and advance through excluded recording windows and thread filters; each selected hit carries the period in `events` units. Every recording, including one that rearms the same sites, starts fresh periods.

A uprobe records the selected instruction's pre-execution context: a hit means execution reached it. The instruction must be proven code of a function described by PE unwind metadata, including chained rows. Certified prolog instructions (PUSH included), body instructions, conditional and direct jumps, and the first instruction of an epilogue are accepted. LOOP, LOOPE, LOOPNE, JRCXZ and JECXZ have only 8-bit displacements: the displaced copy keeps the instruction and lets it branch over a short jump onto a jump to the original target, so counter, ZF and flag behavior stay the original's, and a trap after it is reported where the original lands. XBEGIN is displaced with its abort target rebased. Forms of both with an operand-size prefix, which can truncate the target to 16 bits, reject. Inside a transactional region the processor suppresses the breakpoint and aborts the transaction (Intel SDM, Intel TSX chapter), so a probe there makes the code take its fallback path and records no hit. Faults and traps of displaced code are reported at the original instruction, so the function's own SEH and C++ handlers and other runtimes see real addresses; an unchanged resume continues without a second hit. Other vectored handlers registered after the profiler started see the displaced address. Epilogue interiors reject: Windows recognizes epilogues from code bytes, and an INT3 there would change how it unwinds earlier epilogue positions. Call sites reject, because a displaced CALL pushes a return address outside the module. Code reached only through unresolved indirect jumps also rejects.

A uretprobe needs a function entry or the instruction after its leading ENDBR64. Every RET and leaving jump of the function's complete PE coverage gets one site at the first instruction of its epilogue, where Windows unwinds identically with or without the INT3; the displaced copy reproduces the whole epilogue. Samples use the caller's context after the return, as upstream uretprobes do, so the probed function is not the leaf. A direct branch into an epilogue from code holding exactly the state left at its target, such as a shrink-wrapped early exit from the prolog region to the final RET, is displaced like a body instruction and counts only when taken. A tail jump records its event when it leaves the function rather than when the tail-called function returns. Exceptional exits record nothing. A function rejects when a return path cannot be proven: no unwind metadata (frameless leaf functions), a return reachable only through an unresolved indirect jump, a branch into an epilogue from any other state, or a language-handler function whose call returns to an epilogue start, where an INT3 would make Windows run that handler for the call.

Stop restores every source byte and drains entered capture callbacks. Restored sites release their module lease; their immutable displaced code stays within the bounded site pool. Rearming waits up to one second until no thread can still deliver an earlier trap of the same sites, judged by unwinding each suspended thread through PE metadata; a trap still in exception dispatch fails the start and is never counted later. A walk ends at a frame without PE metadata, so a dispatch beneath such code, for example a vectored handler registered after the profiler that runs JIT code, is not seen. Inspect `windows_software_probe_*` counters for failures, dropped samples and translated exceptions.
Native probe and watchpoint sampling periods are per thread. A new recording starts a fresh period; profiling windows and thread-filter changes preserve its phase, including hits whose output is excluded. For an argument-weighted probe, the selected hit's argument is the weight. Windows also applies thread filters to these probes as an extension to upstream's wall-clock filter contract. `windows_probe_calls` counts hits accepted by the recording/thread gates, while the underlying period still advances through excluded hits.

Profiling windows accept `--begin module.dll!function` and `--end module.dll!function`. Only samples between those calls are collected; the boundaries can repeat. Begin-only starts collection at its first hit. End-only collects until its first hit. Add `--nostop` to keep collecting outside the boundaries while still recording `profiler.Window` markers. These are process-wide windows, not per-thread spans.

The shared Windows breakpoint backend resolves exported names and private C++ names from matching PDBs. Each distinct active address occupies one of x64's four hardware debug-register slots, shared with debuggers; targets at the same address share a slot. Native probes and begin/end boundaries normally require three slots. Explicit TLAB breakpoint profiling also needs two allocation addresses, so combinations beyond the hardware capacity fail at startup. Target DLLs are retained while their breakpoints are active and released during cleanup. `windows_breakpoint_targets` should return to zero after stopping.

Memory watchpoints use `--event mem:0xADDRESS:LENGTH:MODE`. Modes are `w` for writes, `rw` for reads and writes, and `x` for execution. Data lengths are 1, 2, 4, or 8 bytes with matching alignment; execution length is 1. The default is a one-byte read/write watch. Read-only data watchpoints are unavailable on x64 and fail explicitly. `--interval N` keeps every Nth access per thread. Heap addresses are supported, and the caller must keep the watched memory valid for the session.

The helper creates the process suspended with the inherited environment and handles, then queues user APCs on its primary thread. They load each `--preload` DLL in the given order with `LOAD_WITH_ALTERED_SEARCH_PATH`, so a DLL's dependencies are found beside it, and finally call the profiler DLL's `asprof_preload_start` export, which starts the recording described by `ASPROF_COMMAND`. This happens after process initialization, outside the loader lock and before the executable's entry point, so the executable's C runtime initialization is already profiled. Without `ASPROF_COMMAND` the preloaded DLL waits for C API calls; an application that loads the DLL itself never acts on `ASPROF_COMMAND`. A JVM the application creates later is profiled as native code. `--preload` paths are resolved against the current directory. A bare executable name is searched as `CreateProcessW` does: in the helper's directory, the current directory, the system directories and `PATH`. A name with a directory, using either separator, is resolved against the current directory. Either way `.exe` is implied when the file name has no extension. The started process must be x64. The application runs in a job that is killed when the helper exits or is terminated, so processes it leaves in that job end with the helper; ETW companions break away from the job. If a DLL cannot be loaded, its initialization fails, or more than one DLL exports `asprof_preload_start`, the process is terminated before its entry point and the helper prints and returns the Windows error. Otherwise the helper returns the application's exit code; Ctrl+C and Ctrl+Break reach the application while the helper keeps waiting.

Child processes inherit preloading, as upstream's inherited `LD_PRELOAD` and `ASPROF_COMMAND` do. A preloaded process intercepts its `CreateProcess`, `CreateProcessAsUser` and `CreateProcessInternal` imports (W and A), which `ShellExecuteEx` and Java's `ProcessBuilder` also reach. A child whose environment contains `ASPROF_COMMAND` receives the same DLLs through the same early APCs and is then resumed as the caller asked; a child the caller created suspended stays suspended, but its process initialization has already run. Every such descendant starts its own recording, so use `%p` in `file=` to keep the outputs apart, as with upstream. 32-bit children and children created for debugging are skipped with a warning, and a child that cannot load a DLL runs unprofiled after a warning. Processes created elsewhere are not covered: by other processes such as services, COM servers, WMI, Task Scheduler or a shell handler in another process; by the Secondary Logon service for `CreateProcessWithLogonW` and `CreateProcessWithTokenW`; or by direct `NtCreateUserProcess` calls.

Upstream finalizes running recordings from an `atexit` handler. The Windows equivalent intercepts `ExitProcess` with the profiler's other import hooks, so returning from `main` or calling `exit()` stops and writes the recording while the other threads still run. `TerminateProcess` and other abrupt exits bypass it, as `_exit` does upstream.

Windows JVM recordings align profiler timestamps with the JVM counter's origin and tick rate. This is required when combining JVM and profiler JFR chunks: the tested Windows JVMs use elapsed QPC ticks, and a reader can apply the first chunk's clock to subsequent chunks. The span SDK uses that same JVM counter when available; use `Recording.clockFrequency()` to convert SDK tick durations. The tested JVMs kept their 10 MHz QPC clock for both requested clock modes, including with `UseFastUnorderedTimeStamps` enabled.

JVM-free JFR resume keeps the first chunk's clock representation. The requested source still supplies elapsed time; each resumed segment maps it into the existing file's tick rate and wall-clock anchor. This prevents a monotonic/TSC source change from shifting appended samples into the future. Invalid first-chunk clock headers are rejected before appending. `tests/standalone_clock_resume.py` checks both switch directions, timestamps, retained aggregate weights and unchanged files after rejection.

The CLI waits for the program while Ctrl+C reaches only the program, validates its output files and background write errors, prints the profile when `-f` is absent, and exits with the program's exit code. A program that fails before profiling starts, such as a preload failure reported by the helper, leaves its exit code without an output check.

`--timeout TIME` passes a native deadline, such as `30s`, `5m` or a target-local clock time `23:30:00`; `0` disables it. `--loop TIME` rotates recordings on a native relative or absolute schedule; combine it with `--timeout` for a finite run and `%n{MAX}` in the filename for a ring. As upstream, either option turns the default `collect` into `start`: the CLI returns after startup, and the target stops and finalizes the recording at the deadline. Use `-d` when the CLI should wait and stop the recording itself.

As upstream, output options such as `-I`, `-X`, `-s`, `--total`, `--reverse`, `--minwidth`, `--title` and `-o flat=N` apply to `dump` and `stop` exports, and `-t` must be selected when profiling starts.

```powershell
.\asprof dump -f callers.html --total --reverse -I 'com.example.*' 12345
.\asprof stop -f top.txt -o flat=25 12345
```
